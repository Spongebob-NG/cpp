#### 进程的概念与简单命令

##### 进程种类

###### 交互进程

1. shell控制 
2. 与用户实时交互 
3. 绑定终端(占用当前输入/输出流)

例子:在终端里面vim编辑文件 使用命令行调试工具gdb 

###### 批处理进程

1. 不与终端实时交互 
2. 通常被提交到一个任务队列中 由系统根据资源情况自动排队并按顺序批量执行

例子:自动写日志 g++编译器一步到位的编译

###### 守护进程

1. 脱离了终端而存在
2. 随着系统启动而运行 退出而停止

例子:系统日志管理 网络服务进程

##### 特殊的进程

1. 0号进程 linux操作系统启动后运行的第一个进程 当没有其他进程运行的时候会运行这个进程 也叫空闲进程 是1号和2号的父进程
2. 1号进程 **用户态**的秩序管理者 是用户空间的第一个进程 负责必要的硬件与系统初始化工作(挂载文件系统 启动系统日志 拉起网络服务 加载GUI桌面) 并且能收养孤儿进程(父进程退出了 子进程还在运行) 
3. 2号进程 kthreadd(内核线程守护进程)**内核态**的后台打工人队长 是**所有内核线程的祖先 ** **负责内核线程的创建 销毁以及生命周期管理**

**SIGSEGV**

**SIGCHLD**

***易混信号***

**终止类信号**

1. SIGINT  温和的中断 ctrl+c 可捕获  会执行清理逻辑(释放c++内存 关闭数据库连接 触发对象析构等)
2. SIGTERM    是kill默认的命令  功能与SIGINT一样  区别就是SIGINT一般是ctrl+c在当前终端前台程序终止  而kill能给终止指定进程
3. SIGQUIT 退出并吐出堆栈信息  ctrl+`\`  可捕获 与SIGINT最大区别是默认会生成core dump文件  当程序进入死循环  死锁 或者逻辑异常  但是未崩溃时  杀死程序之后能保留现场的内存快照  后续用gdb分析
4. SIGKILL  无条件内核级强制杀死  kill -9  不可捕获   **风险:** 析构函数完全不会被调用  共享内存未解绑 / 互斥锁未释放 / 文件写缓存未flush到磁盘  这些都不会自动处理  除非进程彻底死锁且不响应(SIGINT) 否则不要用

**暂停类信号**

1. SIGTSTP  终端发出的暂停请求  ctrl+z  可捕获  默认挂起  状态变为T-Stopped  可用fg(前台恢复)或者bg(后台恢复)恢复
2. SIGSTOP 无条件内核级强制暂停  Kill -STOP  不可捕获   gdb调试

##### 进程的状态

1. R 运行态/可运行态 不一定此时此刻正在占用CPU 只要在排队等待CPU调度 都是R 
2. **S/D**  休眠态  S能响应中断信号  D不能响应中断信号(即使用kill -9 也无法杀死处于D状态的进程) 
3. T/t  停止态  T:被作业控制信号暂停  通常是kill -STOP 或者按了ctrl+z    t:专属于调试场景
4. Z 僵尸态  进程**占用的内存和文件描述符已经被内核释放**了 但是**PCB里面还保留着PID和退出码**  因为要等父进程wait/waitpid来读取这个退出码  
5. X 死亡态  进程被父进程回收完成  几乎抓不到  

***附加的标志位***

1. `+`前台进程  能直接接收键盘信号  如ctrl+z ctrl+c
2. s 会话首个进程  一般是终端打开时的bash等shell   比如:Ss+ 就是shell正在占据前台等待键盘输入命令  Ss代表shell在后台等待子进程(ps grep或者c++程序)执行完毕
3. l 进程包含多个线程
4. <  高优先级  表示nice<0
5. N  低优先级  表示nice>0
6. L 锁页内存 进程将关键内存锁在物理内存中  禁止被操作系统swap到磁盘

##### 进程退出

**exit / _exit**

其中exit是标准库函数  _exit是系统调用  所以前者会刷新标准IO缓冲区之后再退出  后者是直接退出的

```c++
void exit(int status);
功能：退出当前进程，并刷新当前进程打开的标准IO的缓冲区
参数：进程退出时的状态，会将改制 与 0377进行位与运算后，返回给回收资源的进程
返回值：无
#include <unistd.h>
void _exit(int status);
功能：退出当前进程，不刷新当前进程打开的标准IO的缓冲区
参数：进程退出时的状态，会将改制 与 0377进行位与运算后，返回给回收资源的进程
返回值：无
```

**为什么会跟0377进行与位计算?**

1. 由于POSIX规范以及数据结构限制  传给wait的变量是一个标准的32位整数  其中低16位用于传递退出信息  16位中的**高8位用来表示退出码**  低8位用来表示终止该进程的信号编号  其中**高8位刚好又是exit(status) 中的status跟0377(也就是二进制11111111)与位运算之后截断获得的结果**  
2. 退出码范围控制在0~255之间 0代表程序正常退出 1~255代表各种不同原因的异常/错误退出   其中1~125是程序员自己定义的 128+N是进程被信号N终止时的退出码   比如说被SIGINT(2)杀死  那么退出码就是130

##### 进程资源回收

**wait / waitpid**

其中wait是阻塞回收任意一个子进程资源  waitpid可以阻塞也可以非阻塞地回收指定进程号的资源(当然了也可以回收任意的)

```c++
#include <sys/types.h>
#include <sys/wait.h>
pid_t wait(int *status);
功能：阻塞回收子进程的资源
参数：接收子进程退出时的状态，获取子进程退出时的状态与0377进行位与后的结果，如果不愿意
接收，可以填NULL
返回值：成功返回回收资源的那个进程的pid号，失败返回-1并置位错误码
pid_t waitpid(pid_t pid, int *status, int options);
功能：可以阻塞也可以非阻塞回收指定进程的资源
参数1：进程号
>0:表示回收指定的进程，进程号位pid（常用）
=0：表示回收当前进程所在进程组中的任意一个子进程
=-1：表示回收任意一个子进程（常用）
<-1:表示回收指定进程组中的任意一个子进程，进程组id为给定的pid的绝对值
参数2：接收子进程退出时的状态，获取子进程退出时的状态与0377进行位与后的结果，如果不愿
意接收，可以填NULL
参数3：是否阻塞
0：表示阻塞等待 ：waitpid(-1, &status, 0);等价于 wait(&status)
WNOHANG：表示非阻塞
返回值：
>0: 返回的是成功回收的子进程pid号
=0:表示本次没有回收到子进程
=-1：出错并置位错误码
```

#### 进程间通信(IPC)

**为什么只能通过外部文件或者内核空间来进行进程间通信呢?** 

因为多个进程的用户空间是相互独立的  

##### 内核提供的通信方式

**文件类型:** b 块设备文件  c 字符设备文件 d 目录文件(文件夹) - 普通文件 l 链接文件 s 套接字文件(网络编程) p 管道文件

###### 无名管道

是在内核空间创建出来一个管道通信  随着进程的结束而消失  并且只适用于亲缘进程之间通信 不适用于非亲缘进程

**pipe**

```c++
#include <unistd.h>
int pipe(int fildes[2]);
功能：创建一个无名管道，并返回该管道的两个文件描述符
参数：是一个整型数组，用于返回打开的管道的两端的文件描述符， fildes[0]表示读端
fildes[1]表示写端
返回值：成功返回0，失败返回-1并置位错误码
    
1、管道可以实现自己给自己发消息
2、对管道中数据的操作是一次性的，当管道中的数据被读取后，就从管道中消失了，再读取时会被阻塞
3、管道文件的大小：64K
4、由于返回的是管道文件的文件描述符，所以对管道的操作只能是文件IO相关函数，但是，不可以使用
lseek对光标进行偏移，必须做到先进先出
5、管道的读写特点：
当读端存在时：写端有多少写多少，直到写满64k后，在write处阻塞
当读端不存在时：写端再向管道中写入数据时，会发生管道破裂，内核空间会向用户空间发射一个
SIGPIPE信号，进程收到该信号后，退出
当写端存在时：读端有多少读多少，没有数据，会在read出阻塞
当写端不存在时：读端有多少读多少，没有数据，不会在read处阻塞了
6、管道通信是半双工通信方式
单工：只能进程A向B发送消息
半双工：同一时刻只能A向B发消息
全双工：任意时刻，AB可以互相通信
```

###### 有名管道

既可以亲缘间通信 也能非亲缘间通信  并且会在文件系统中创建出来一个真实存在的管道文件

**注意!** 

**有名管道的数据通信也发生在内核空间** 数据绝不会落到磁盘上  那个**磁盘文件只是作为一个门牌号**(索引)  因为**无名管道能直接fork()让子进程继承父进程的文件描述符来找到同一个内核缓冲区**  但是**有名管道不能直接继承**  所以为了让非亲缘间通信  就必须要有这个"门牌号" 内核就能把两个通信进程打开的文件描述符 指向同一个内核空间的缓冲区里面

**mkfifo**

```c++
#include <sys/types.h>
#include <sys/stat.h>
int mkfifo(const char *pathname, mode_t mode);
功能：创建一个管道文件，并存在与文件系统中
参数1：管道文件的名称
参数2：管道文件的权限，内容详见open函数的mode参数
返回值：成功返回0，失败返回-1并置位错误码
注意：管道文件被创建后，其他进程就可以进行打开读写操作了，但是，必须要保证当前管道文件的
两端都打开后，才能进行读写操作，否则函数会在open处阻塞
```

##### 信号

**信号的处理方式: 捕获 忽略 默认**

###### 信号处理函数

**signal**

```c++
#include <signal.h>
typedef void (*sighandler_t)(int);
sighandler_t signal(int signum, sighandler_t handler);
功能：将信号与信号处理方式绑定到一起
参数1：要处理的信号
参数2：处理方式
SIG_IGN：忽略
SIG_DFL：默认，一般信号的默认操作都是杀死进程
typedef void (*sighandler_t)(int)：用户自定义的函数
返回值：成功返回处理方式的起始地址，失败返回SIG_ERR并置位错误码
注意：只要程序与信号绑定一次，后续但凡程序收到该信号，对应的处理方式就会立即响应
```

**怎么理解typedef void (*sighandler_t)(int)?**

这里先来介绍一下c语言的一个概念  **声明即使用**  就是说  假设有一个指向int类型的指针变量p  对它进行解引用的操作就是`*`p 然后得到的类型就是int类型  所以声明指针变量p的时候  就是int *p  满足声明即使用

现在再来看函数指针和普通函数的区别  如果是void`*`func(int) 就代表这是个名为func的函数 返回类型是void`*` 参数类型是int  但是如果把`*`和func用括号括在一起  也就是void (`*`func)(int)的话 就代表这是个函数指针  指向的函数 类型是void 参数是int  **怎么理解void (`*`func)(int)是个函数指针呢?**   首先知道func是一个函数指针 然后对它解引用 也就是`*`func之后 得到一个函数   然后调用这个函数 就在后面传个int类型的参数 (`*`func)(int)  所以声明这个函数的时候 跟调用这个函数的形式是一样的 只不过前面加上这个函数的返回类型就行了 也就是void

如果说不typedef的话  signal函数的形式应该是 void(`*`signal(int signum,void(*handler)(int)))(int)  handler是形式参数 类型是函数指针 接收的是新的处理函数的地址  **然后signal要注意 是函数而不是函数指针! 只不过signal函数的返回类型是函数指针罢了**  并且返回的地址是旧的处理函数  就好像int cal_sum(int a),传的参数类型是int 然后cal_sum是个函数而不是指针 返回的类型是int  本质其实是一样的 只不过这里比较绕而已

**怎么理解handler也要传个signum进去?**

signal函数的流程是这样的:  先把handler函数注册到内核里面  只要收到signum这个信号  就调用后面的handler  此时handler还没有真正被执行   等到signum这个信号正式触发的时候  handler的signum是被内核自动填进去的! 至于为什么还要填进去一个signum参数 而不是直接调用  是因为**同一个handler 可能处理多个不同的信号!**

```c++
void clean_and_exit(int sig) {
    if (sig == SIGINT) {
        std::cout << "用户按下了 Ctrl+C，正在保存数据退出..." << std::endl;
    } else if (sig == SIGTERM) {
        std::cout << "收到 kill 终止命令，正在断开机器人连接退出..." << std::endl;
    } else if (sig == SIGHUP) {
        std::cout << "终端挂起，正在重新加载配置文件..." << std::endl;
    }
    exit(0);
}
```

###### 对僵尸进程进行回收

```c++
void handler(int signo)
{
    if(signo == SIGCHLD)
    {
        //回收僵尸进程
		while(waitpid(-1, NULL, WNOHANG) > 0);
	}
}
int main(int argc, const char *argv[])
{
//当子进程退出后，会向父进程发送一个SIGCHLD的信号，我们可以将其捕获，在信号处理函数中将子进程资源回收
if(signal(SIGCHLD, handler) == SIG_ERR)
{
	perror("signal error");
	return -1;
}
    ...
}
```

**注意事项**

其中 **while(waitpid(-1, NULL, WNOHANG) > 0);** 是非阻塞回收子进程 为什么要这样呢 首先如果同时有多个子进程结束的话 可能只会发送一次SIGCHLD信号  因为**SIGCHLD是不可靠信号**  如果不用while的话 只会回收一个子进程 其他的子进程就会变成僵尸进程. 那为什么要非阻塞呢? 如果是while(wait(nullptr)>0)的话 如果没有子进程被回收 父进程就会一直卡在wait这里  影响父进程的执行

###### 不可靠信号与可靠信号

1~31是不可靠信号(标准信号/非实时信号)  34~64是可靠信号(实时信号)

区别

1. 不可靠信号是基于**位图**来存储的  只用一个32位的整数位图来记录这些信号 每个信号占1个比特  如果短时间内同一个信号发了很多次 内核只会把这一位重复写为1 不支持排队
2. 可靠信号是基于**链表队列**存储的 不会发生覆盖或丢失

##### 消息队列

**msgget**

```c++

#include <sys/ipc.h>
```

##### 销毁消息队列

**msgctl**

```c++
#include <sys/types.h>
#include <sys/ipc.h>
#include <sys/msg.h>
int msgctl(int msqid, int cmd, struct msqid_ds *buf);
功能：对给定的消息队列执行相关的操作，该操作由cmd参数而定
参数1：消息队列的ID号
参数2：要执行的操作
IPC_RMID：删除一个消息队列，当cmd为该值时，第三个参数可以省略填NULL即可
IPC_STAT：表示获取当前消息队列的属性，此时第三个参数就是存放获取的消息队列属性
的容器起始地址
IPC_SET：设置当前消息队列的属性，此时第三个参数就是要设置消息队列的属性数据的起
始地址
参数3：消息队列数据容器结构体，如果第二个参数为IPC_RMID,则该参数忽略填NULL即可 如果是其他的话 就要填入一个结构体 结构体的详细内容这里就不列出了 里面记录了最后一次发送消息的进程pid 时间等各种信息
```

**注意事项**

1. 消息分为两部分 消息类型和消息正文  这个结构体由用户自己定义
2. 任何一个进程可以向消息队列中发消息 也可以取消息
3. 多个进程用相同的key打开的是同一个消息队列 (而且这意味着每个进程都需要事先创建出来一个消息队列)
4. 读取了消息之后 这个消息就不存在了

