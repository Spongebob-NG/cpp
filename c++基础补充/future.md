## 现代 C++ 异步核心：std::future 进阶复习笔记

### 一、核心架构与内存模型

`std::future` 是 C++11 引入的**单次结果异步检索通道的只读端**。它本身不直接分配线程，也不直接持有计算数据，而是通过指针索引底层的**控制块（Shared State，共享状态）**。



#### 1. 共享状态（Shared State）的物理构成

- **生命周期**：由堆内存管理，内部维护原子引用计数（`std::atomic< size_t >`）。写端（如 `std::promise`）与读端（`std::future`）共同持有该控制块的生命周期引用。
- **数据槽位**：`union` 结构，存储正常返回值类型 `T` 或异常指针 `std::exception_ptr`。
- **同步原语**：内嵌互斥锁与条件变量，用于阻塞和唤醒处于 `get()` 或 `wait()` 状态的读端线程。
- **状态机**：标志位记录状态转换：`Not Ready` $\to$ `Ready` $\to$ `Retrieved`。

#### 2. 三种数据提供端（Providers）

- **`std::async`**：高阶抽象，负责底层线程创建/调度，直接返回关联的 `std::future< T >`。
- **`std::packaged_task< R(Args...) >`**：可调用对象包装器，将函数执行与共享状态绑定，常用于线程池中的任务封装。
- **`std::promise< T >`**：最底层的显式管道端，开发者在任意线程手动调用 `set_value()` 或 `set_exception()` 填充状态。

#### 3. 消费端演进：std::future vs std::shared_future

- **`std::future< T >`**：**独占所有权**（Move-only，禁拷贝）。只能有一个消费者，调用 `get()` 会移动数据并销毁关联。
- **`std::shared_future< T >`**：**共享所有权**（Copy-constructible）。多线程并发读取同一份数据时使用，调用 `get()` 返回常引用 `const T&`，不会使状态失效。通过 `fut.share()` 转换获得。

### 二、核心 API 与状态机行为

| **API 名称**       | **行为机制**                                                 | **调用约束**                                         | **错误码/异常**                                             |
| ------------------ | ------------------------------------------------------------ | ---------------------------------------------------- | ----------------------------------------------------------- |
| **`get()`**        | 阻塞等待共享状态就绪；返回移动/复制的数据，或在调用线程重新抛出异常 | **仅能调用一次**。调用后 `valid() == false`          | 二次调用抛出 `std::future_error`（`future_errc::no_state`） |
| **`wait()`**       | 仅阻塞等待共享状态进入 `Ready`，不取出数据，不改变内部数据所有权 | 可重复多次调用，调用后 `valid()` 仍为 `true`         | 无                                                          |
| **`wait_for()`**   | 接收相对时间 `std::chrono::duration`，进行非阻塞/超时轮询    | 嵌入式/机器人高频主循环常用，防止任务饿死            | 返回 `std::future_status`（见下文）                         |
| **`wait_until()`** | 接收绝对时间戳 `std::chrono::time_point`，超时等待           | 适用于系统级时间基准对齐场景                         | 返回 `std::future_status`                                   |
| **`valid()`**      | 检查当前对象内部是否关联有效的共享状态                       | 无副作用，调用 `get()` 或 `std::move` 后变为 `false` | 无                                                          |

#### `std::future_status` 状态枚举值（wait_for 返回值）

1. `std::future_status::ready`：任务已经完成，可无阻塞调用 `get()`。
2. `std::future_status::timeout`：设定的等待时间已耗尽，数据仍未就绪。
3. `std::future_status::deferred`：任务被推迟执行，底层没有并发线程，等待 `get()` 触发同步执行。

### 三、std::future 与 条件变量/互斥锁 的对比选型

| **维度**             | **std::condition_variable + std::mutex**                    | **std::future / std::promise**                               |
| -------------------- | ----------------------------------------------------------- | ------------------------------------------------------------ |
| **本质定位**         | 底层线程同步原语                                            | 高层异步数据传递管道                                         |
| **返回值与生命周期** | 需要额外定义全局或共享变量，手动管理堆栈生命周期            | 强类型数据载体，自动移动构造并管理控制块内存                 |
| **跨线程异常传递**   | **不可直接传递**。子线程异常未捕获直接触发 `std::terminate` | **原生支持**。异常以 `std::exception_ptr` 形式捕获，并在 `get()` 处重抛 |
| **使用频次模型**     | **多对多、无限次循环复用**（适合持续数据流）                | **一次性通道**（消费即废弃，适合请求-响应）                  |
| **经典工程场景**     | 线程池任务队列、相机高频帧 Ring Buffer、事件循环            | 算法离线单次计算、传感器请求应答、服务配置拉取               |

### 四、面试三大高频“深坑”与底层成因

#### 1. 临时对象析构阻塞（`std::async` 同步退化）

- **表象**：写了多行 `std::async(std::launch::async, task);`，后台没有并发，代码耗时等于各项任务耗时累加。
- **物理成因**：没有使用具名变量接收返回值。生成的临时 `std::future` 在当前语句分号结束后立刻执行析构函数；标准规定，由 `std::async` 产生且尚未就绪的 `future`，其析构函数**必须强制阻塞等待底层线程执行结束**。
- **解法**：必须使用左值变量接住返回值：`auto fut = std::async(...);`。

#### 2. 默认策略退化为惰性求值（Deferred Execution）

- **表象**：调用 `std::async(task)` 后，子线程任务根本没有提前运行；若业务后续分支未调用 `get()`，任务完全不执行。
- **物理成因**：默认策略是 `std::launch::async | std::launch::deferred`。系统如果判断当前线程负载较高，会自动选择 `deferred` 策略，将任务延迟到后续 `get()` 调用的线程上同步执行。
- **解法**：在工程代码中永远显式指明策略，强制并发使用 `std::launch::async`。

#### 3. Broken Promise（管道异常破损）

- **表象**：消费者线程在 `fut.get()` 处崩溃，抛出 `std::future_error`（`Broken promise`）。
- **物理成因**：持有 `std::promise` 的生产端线程在控制流中提前 `return` 或遭遇未捕获异常退出，导致 `std::promise` 被析构，而期间从未调用 `set_value()` 或 `set_exception()`。控制块检测到写端断开且未准备就绪，自动注入 `broken_promise` 异常以唤醒读端，防止其永久死锁。
- **解法**：生产端代码必须使用 `try-catch` 闭环，在异常分支中显式调用 `prom.set_exception(std::current_exception())`。

### 五、面试速查与应答话术

- **Q: `std::future::get()` 会发生什么？可以调用两次吗？**
  - **A**: 会阻塞调用线程直至状态就绪，随后将值 Move 给调用方，或将子线程异常在当前线程重抛。**不可调用两次**。内部共享状态在调用后标记为已消费，再次调用会抛出 `no_state` 的 `std::future_error`。
- **Q: 如果只需要同步信号，不需要返回值，`future` 该怎么写？**
  - **A**: 使用模板特化 `std::future< void >` 和 `std::promise< void >`。写端调用 `prom.set_value()`，读端调用 `fut.wait()` 或 `fut.get()` 即可实现纯事件同步，不需要构造哑变量。
- **Q: ROS2 / 中间件客户端在通信时为什么常用 `spin_until_future_complete`？**
  - **A**: 服务通信基于请求-响应机制。底层通信节点发起异步 Service Request 时获得一个 `std::shared_future`，随后主线程不能盲目死等 `fut.get()`（否则无法响应中断和其它回调），而是通过 `spin_until_future_complete` 结合事件循环与超时机制来维持执行器的活性。
